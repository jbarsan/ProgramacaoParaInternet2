# Relatório de Aprendizado

## João Carlos B. Santos

Quando comecei a desenvolver este projeto da tabela de produtos, a primeira coisa que realmente mudou na minha cabeça foi entender o que significa um frontend reativo na prática. Antes, quando fazíamos páginas mais simples, parecia que tínhamos que controlar tudo no braço: descobrir qual parte da tela mudou, apagar linhas da tabela e desenhar tudo de novo manualmente. Neste trabalho, percebi que a ideia da programação reativa é muito mais natural: a tela é apenas um reflexo dos dados que temos naquele momento. Quando eu digito "Maçã" na caixa de pesquisa ou marco a opção de ver apenas o que tem em estoque, eu não preciso mandar o navegador esconder linha por linha; eu apenas atualizo o valor da busca e a própria interface reage sozinha, redesenhando a lista na mesma hora.

Depois de ver a tela funcionando, ficou claro para mim por que precisamos de um backend com uma API RESTful. Se os produtos ficassem guardados apenas no navegador, qualquer alteração sumiria assim que alguém recarregasse a página. Ao construir o servidor (`produtos-api`) conectado a um banco de dados SQLite, aprendi como o frontend e o backend conversam pela internet de um jeito organizado. Em vez de inventar nomes confusos para cada ação, usamos um endereço único para os produtos (`/api/products`) e deixamos o próprio tipo de pedido dizer o que queremos fazer: buscar a lista, cadastrar um item novo, editar, mandar uma foto ou excluir, recebendo sempre um código de resposta claro que avisa se deu tudo certo ou se aconteceu algum problema.

Enquanto montava esse servidor, entendi por que dividir o código em camadas e validar tudo na entrada faz tanta diferença. No começo, a vontade de quem está aprendendo é colocar a rota, a regra e o comando do banco de dados todos juntos no mesmo lugar para ver funcionar logo. Mas ao separar cada responsabilidade em sua própria pasta — uma parte só para receber o pedido, outra para pensar nas regras e outra só para conversar com o banco — o código ficou muito mais fácil de ler e de consertar. Além disso, aprendi a colocar uma conferência logo na porta de entrada da API para checar se o produto tem nome, categoria e preço certos, e se a foto enviada é realmente uma imagem leve, barrando dados errados antes mesmo de chegarem perto do banco de dados.

Dando um passo além nessa organização, aplicar os conceitos de DDD e da Arquitetura Hexagonal neste projeto me ajudou a enxergar onde mora o que é mais importante no sistema. Falando de um jeito simples, a ideia foi deixar o coração do projeto — o que é um Produto, o que é um Usuário e quais regras eles seguem — totalmente protegido no centro do código, sem depender de nenhuma ferramenta externa. O banco de dados, a criptografia de senha e o servidor web ficaram nas bordas, funcionando como peças que se encaixam nesse centro. Foi interessante ver como o banco podia guardar os nomes das colunas de um jeito e a camada externa traduzia tudo para o jeito que o nosso centro e o nosso frontend preferem, sem misturar as coisas.

Por fim, aplicar os conceitos de *Thinking in React* foi essencial para entender os fundamentos do React de um jeito muito concreto. Aprendi a olhar para uma tela inteira e quebrá-la em pedaços menores, onde cada componente cuida de uma tarefa simples: uma linha para o título da categoria, uma linha para o produto (que fica vermelha quando acaba o estoque), a tabela que junta essas linhas, a barra de pesquisa e o quadro principal que coordena tudo. O maior aprendizado foi perceber que não precisamos guardar na memória do React a lista filtrada, porque ela pode ser calculada na hora a partir da lista original, do texto digitado e da caixinha de estoque. Guardar esses dados no componente principal e passar para os componentes filhos — enquanto a barra de busca avisa o componente pai quando o usuário digita — fez tudo fazer sentido do começo ao fim.

Também pude utilizar as técnicas de desenvolvimento com agentes de IA ensinadas pelo professor e que me ajudaram bastante. Todo os passos estão relatados no documento IA.md, e as instruções para o agente estão no arquivo AGENTS.md.

Desenvolver com agentes de IA me ajudou a entender melhor como utilizar essas ferramentas de forma eficiente. As instruções detalhadas e as discussões sobre os limites do uso de IA foram essenciais para que eu pudesse aproveitar ao máximo os benefícios dessa tecnologia sem comprometer a qualidade do meu trabalho.
